# Retail DW: DataStage → Databricks migration

This folder migrates the 23-job DataStage retail warehouse pipeline (`pipeline/`, exported to
`DataStage Jobs/Pipeline/*.dsx`) to Databricks.

It covers **the tools and terms used** (§0), **what was built** (design), **how we got there** (the
journey, including the dead ends) and **what is still open**.

---

## 0. Background: the pieces and the terms

### The source

- **IBM DataStage**: the ETL tool the pipeline was written for. A *parallel job* is a data flow of
  *stages* (file read, Transformer, Join, Aggregator, …) connected by *links*. A *sequence job* orchestrates
  parallel jobs. This repo's jobs were generated by `pipeline/generate.py` and exported as **DSX**, DataStage's
  text export format. Databricks tools expect the other export format, **XML**.

### The Databricks Labs tools

- **[Lakebridge](https://databrickslabs.github.io/lakebridge/)** ([repo](https://github.com/databrickslabs/lakebridge))
  is Databricks Labs' migration toolkit. We used three of its parts:
  - **[Analyzer](https://databrickslabs.github.io/lakebridge/docs/assessment/analyzer/)**: reads the source
    exports and produces an Excel assessment (jobs, stages, complexity, functions used). Pre-migration analysis.
  - **[BladeBridge](https://databrickslabs.github.io/lakebridge/docs/transpile/pluggable_transpilers/bladebridge/)**:
    Lakebridge's rule-based *transpiler*, a code converter. For DataStage it is meant to turn each XML-exported
    job into a Databricks notebook and each sequence into a Workflow
    ([DataStage guide](https://databrickslabs.github.io/lakebridge/docs/transpile/source_systems/datastage/)).
    **For this repo it produced no notebooks** (§3).
  - **[Switch](https://databrickslabs.github.io/lakebridge/docs/transpile/pluggable_transpilers/switch/)**:
    Lakebridge's *LLM-based* transpiler (experimental). It uploads the source files and runs a Databricks Job that
    sends each file to a Foundation Model with a conversion prompt, then writes the generated notebooks to the
    workspace. The prompt can be replaced with a
    [custom prompt](https://databrickslabs.github.io/lakebridge/docs/transpile/pluggable_transpilers/switch/customizing_switch/),
    which is what made it work here.
- **[DQX](https://databrickslabs.github.io/dqx/)** ([repo](https://github.com/databrickslabs/dqx)) is Databricks
  Labs' data-quality framework for PySpark. Rules ("checks") are declared as metadata and applied by a `DQEngine`.
  Failing rows are reported in `_errors` / `_warnings` columns or quarantined, and
  [summary metrics](https://databrickslabs.github.io/dqx/docs/guide/summary_metrics/) are written to a table.
  We used it three times: to [profile](https://databrickslabs.github.io/dqx/docs/guide/data_profiling/) the
  source files, to [validate](https://databrickslabs.github.io/dqx/docs/guide/quality_checks_apply/) each
  migrated run, and to reconcile the two implementations
  ([`compare_datasets`, `has_valid_schema`](https://databrickslabs.github.io/dqx/docs/reference/quality_checks/)).

### The Databricks platform pieces

- **[Declarative Automation Bundles](https://docs.databricks.com/dev-tools/bundles/)** (Asset Bundles):
  `databricks.yml` + resource YAML that deploys notebooks and jobs with `databricks bundle deploy`.
- **[Lakeflow Jobs](https://docs.databricks.com/aws/en/jobs/)**: the scheduler/orchestrator that replaces the
  DataStage sequence (tasks, dependencies, condition tasks).
- **[Unity Catalog](https://docs.databricks.com/aws/en/data-governance/unity-catalog/)**: tables live in
  `catalog.schema.table`, and the source CSVs sit in a
  [volume](https://docs.databricks.com/aws/en/volumes/) (`/Volumes/unitygo/retail_dw/landing`).

### Terms used in this doc

| Term | Meaning |
|---|---|
| **compiler**, **compiled version** | `ds2spark.py`, written for this migration because BladeBridge produced nothing. It is not a Lakebridge tool. It reads the job definitions in `pipeline/pipeline_def.py` (the model that also generates the DSX) and emits one Databricks notebook per job by fixed rules (§2.1, §2.3). Same input, same output, every time. |
| **Switch version** | The notebooks Switch generated from the DSX exports, using our custom prompt. |
| **SDP version** | A third implementation: Switch with `target_type: sdp` generated one [Spark Declarative Pipeline](https://docs.databricks.com/aws/en/dlt/) source file per job, all deployed as **one** pipeline. SCD2 is done with Auto CDC from snapshots (§7). |
| **two implementations** | The compiled and Switch versions were both deployed and run, each to its own schema, so each could be checked against the other with DQX. The rule-based and LLM routes are both kept: the compiled version is the deterministic reference, and the Switch version shows what Lakebridge's supported tool produces. |
| **validation** | DQX rules on the migrated tables of *one* run (not-null, uniqueness, value ranges, foreign keys …), §5. |
| **reconciliation** | DQX check that the Switch run's tables equal the compiled run's tables, row for row, §6. |

### 2.1 Mapping DataStage to Databricks

| DataStage | Databricks |
|---|---|
| Parallel job | One Python notebook (`src/notebooks/Jxx_*.py`) |
| Link | One temp view named like the link, built with `spark.sql(...)` |
| Sequential File source, `#pSrcDir#/*.csv` | `spark.read.csv` from the UC volume `unitygo.retail_dw.landing`, **columns renamed by position**, empty strings preserved (§4) |
| Sequential File target or intermediate file (`#pStgDir#`, `#pDwhDir#`, `#pMartDir#`, `#pAuditDir#`) | Delta table `{catalog}.{schema}.<file stem>` (overwrite; append where the stage appends) |
| Transformer derivation | `SELECT CAST(<expr> AS <type>)`, with expressions translated (§2.3) |
| Filter / Join / Aggregator / Sort / Remove Dups / Head / Copy / Funnel | `WHERE` / `JOIN` / `GROUP BY` / `ORDER BY` / `row_number()=1` / `ORDER BY … LIMIT` / extra view / `UNION ALL` |
| Surrogate-key idiom `@PARTITIONNUM + (@NUMPARTITIONS * (@INROWNUM-1)) + 1` | `row_number() OVER (ORDER BY <upstream sort>)` |
| Job parameters | Notebook widgets `catalog`, `schema`, `src_dir`, `pRunDate`, `pEffDate` |

### 2.2 Mapping the master sequence to a Lakeflow Job

`build_bundle.py` generates `resources/retail_dw_job.yml` from `pipeline/pipeline_dag.json`.

| Sequence activity | Job task |
|---|---|
| `act_Prepare_Dirs` + `wff_Source_Orders` | `setup` notebook: creates the schema and waits up to 10 min for the 11 source files |
| `run_Jxx` job activities | `notebook_task` per job |
| `seq_*` sequencers (ALL) | Folded into `depends_on` |
| `act_Check_Dim_Customer` (exec: file exists?) | `check_dim_customer` notebook → task value `dim_state` |
| `run_J05` with custom trigger `= "MISSING"` | `condition_task` `cond_dim_missing` → J05 runs on `true` |
| `seq_Dim_Customer_Ready` (ANY) | J06 `run_if: NONE_FAILED`, depends on J05 and the check |
| `act_Promote_Dim_Customer` (`mv` file) | `promote_dim_customer`: `CREATE OR REPLACE TABLE dim_customer AS SELECT * FROM dim_customer_next` |
| `seq_All_Done` | `dqx_validate` (depends on J14–J23) |
| `exc_Any_Failure`, `act_Notify_*`, `term_Abort` | **Not migrated.** No job notifications are configured yet (§8) |

### 2.3 Expression translation (`ds2spark.py`)

A recursive-descent parser translates DataStage expressions into Spark SQL. It handles
`If … Then … Else` → `CASE`, `And`/`Or`, the `:` concatenation operator, and these functions:
`Trim, Upcase, Downcase, Len, Abs, Left, NullToValue, IsNull, Ereplace, CRC32, StringToDecimal,
StringToDate, StringToTimestamp, DateToString, TimestampToString, DaysSinceFromDate, DateFromDaysSince`.
Date formats are mapped too (`%yyyy%mm%dd` → `yyyyMMdd`, `%nn` → minutes). An unknown function raises an
error instead of being passed through silently.

## 3. Journey

### Phase 1: analysis

1. **DSX to XML.** The Lakebridge Analyzer and BladeBridge read only DataStage *XML* exports. The repo only had
   DSX, and no DataStage server was available to re-export. `dsx_to_xml.py` started as a line-based converter.
   It was then rewritten as a tokenizer/parser that follows the DSX grammar from
   [jdelvign/dsxparser](https://github.com/jdelvign/dsxparser) (`DSX.g4`). The rewrite keeps every block
   (`DSJOB`, `DSSTAGETYPES`, `DSTABLEDEFS`, `DSROUTINES`, `DSSHAREDCONTAINER`, `DSUBINARY`); the first version
   dropped everything except `DSJOB`.
2. **Lakebridge Analyzer** (`bladespector`, run on the XML) → `analysis/lakebridge-analyzer.xlsx`:
   24 jobs, 946 nodes. Complexity: **VERY_HIGH** 5 (J06 SCD2, J10 Fact Sales, J17 Customer 360,
   J22 DQ checks, the master sequence), **HIGH** 17, **MEDIUM** 2 (J05, J12). Marked *supported*:
   Sequential File, Filter, Join, Aggregator, Copy, Sort, Remove Duplicates, Funnel, Job Activity, Sequencer.
   Marked *not supported*: `CTransformerStage` and `CCustomStage` (even though the Lakebridge docs list
   Transformer as supported), plus the exec-command, notify, wait-for-file, terminator and exception-handler
   activities.
3. **DQX source profiling** (`_dqx_profile_sources`): `DQProfiler` + `DQGenerator` over the 11 source CSVs,
   from 12 rows (suppliers) to 33,732 rows (orders). Candidate rules: 2–23 per file. Results are in
   `unitygo.retail_dw.dq_source_profile`. The candidates are not applied as-is. The validation rules (§5) were
   written by hand from the DataStage job logic, and the candidates are kept for review.

### Phase 2: conversion

| Attempt | Result |
|---|---|
| **BladeBridge** (Lakebridge's DataStage transpiler, pip `databricks-bb-plugin`, binary run directly) | Parses the XML (finds the job, nodes and links) but generates **no notebooks**. Its only output is `databricks_conversion_supplements.py`. The official `lakebridge transpile` CLI fails with `Client has not yet registered its transpile capability`. **Unresolved**: without one genuine Designer XML export we cannot tell whether the XML shape or the tool is at fault. |
| **Compiler** (`ds2spark.py`, see §0) | Reads the in-memory job model (`pipeline/pipeline_def.py`, the same model that generates the DSX). Deterministic. Became the reference implementation. |
| **Switch #1**, built-in `unknown_etl` prompt | 24/24 "converted" with no errors, but produced [Spark Declarative Pipeline](https://docs.databricks.com/aws/en/dlt/) code: only 1 of 24 files had `@dp` decorators, references to tables that are never created, Windows paths left in, and an invented master-sequence notebook. **Unusable.** |

(`switch_input/J05_Dim_Customer_Initial.txt`):

```text
STAGE xfm_Version1  [CTransformerStage]
    in  link lnk_stg  <-> src_stg_customers_2010
```

### Switch prompts, attempt by attempt

Every attempt used model `databricks-claude-sonnet-5-5`, `source_format: generic` (no SQL preprocessing),
`target_type: notebook`, `max_fix_attempts: 1`, `concurrency: 4`, `--source-dialect unknown_etl`, and the
condensed inputs above. What changed between attempts is the prompt, the few-shot examples and `request_params`.
Each system message is kept in [`switch_prompt/history/`](switch_prompt/history/) so they can be diffed.
The final prompt (system message + few-shots) is
[`switch_prompt/datastage_to_notebook.yml`](switch_prompt/datastage_to_notebook.yml), generated by
[`build_prompt.py`](switch_prompt/build_prompt.py).

| # | Prompt | Few-shots | `request_params` | Tokens | Result |
|---|---|---|---|---|---|
| 1 | Built-in `etl_to_lakeflow_sdp/unknown_etl.yml` | – (built-in) | – | 282k | Unusable SDP code (see below) |
| 2 | Custom, [`system_attempt2.txt`](switch_prompt/history/system_attempt2.txt) | J05, J04 | – | 485k | Correct structure. 4 Top-N views lost `ORDER BY`; CSV columns read by name |
| – | Same as #3 | J04, J15 | `thinking: {type: enabled, budget_tokens: 16000}` | 0 | All 23 calls rejected: HTTP 400 `"thinking.type.enabled" is not supported for this model` |
| 3 | Custom, [`system_attempt3.txt`](switch_prompt/history/system_attempt3.txt) | J04, J15 | `thinking: {type: adaptive}`, `output_config: {effort: high}`, `max_tokens: 64000` | 523k | 0 lost `ORDER BY`, 11/11 positional reads. Empty-field bug still present (inherited from the compiler) |
| 4 | Custom, [`system_attempt4.txt`](switch_prompt/history/system_attempt4.txt) (final) | J04, J15 (regenerated) | as #3 | 526k | Matches the compiled version on 39/39 tables after running |

**Attempt #1, built-in `unknown_etl` prompt.** In Switch, `--source-dialect` picks a *prompt family*.
`unknown_etl` belongs to the `etl_to_lakeflow_sdp` family. Its system message begins *"Convert ETL workload code to
Lakeflow Spark Declarative Pipeline … code in `${language}`"*, and `${language}` is only filled in when
`target_type: sdp`. With `target_type: notebook` the model got the SDP instructions with the placeholder left in,
and said so in its output ("The `${language}` placeholder in the request was not filled in"). It wrote functions
without `@dp` decorators, guessed the master sequence's logic from job names, and kept the Windows paths.
*Lesson: for plain notebooks from an ETL source that isn't built in, provide your own prompt through
`conversion_prompt_yaml`.*

**Attempt #2, first custom prompt** ([full text](switch_prompt/history/system_attempt2.txt)). Its sections:

1. *Input and Output*: the input is one condensed job. The output is plain batch-notebook Python. It
   explicitly forbids `dp.table` / `pyspark.pipelines`, and says "never invent logic".
2. *Parameters*: the **exact** widget block to start with, plus how each DataStage directory parameter maps
   (`#pSrcDir#` → `src_dir`; other directories → Delta tables).
3. *Stages → code*: one rule per stage type (source, target, Transformer, Filter, Join, Aggregator, Sort, Remove
   Duplicates, Head, Copy, Funnel, surrogate-key idiom), the column-type mapping, and "one temp view per
   link, named like the link".
4. *DataStage functions → Spark SQL*: the same mapping table the compiler uses, including date-format tokens.
5. *Style*: no SparkSession, a comment per stage, row counts after writes.

Few-shots: two (condensed job → compiled notebook) pairs. Effect: the declarative-pipeline output disappeared,
along with the `C:/` paths and the invented logic. All 23 notebooks had the same views, reads and writes as the
compiled version. Two problems remained:
- *Head after Sort lost the order.* The rule said `Head: LIMIT n`, and neither example contained a Sort feeding
  a Head. So `Top 50 products` became an arbitrary 50.
- *CSV columns read by name.* The examples showed the compiler's by-name read, which was itself a bug. Switch copied it.

**Attempt #3, three changes made together** ([full text](switch_prompt/history/system_attempt3.txt);
diff against #2: `diff switch_prompt/history/system_attempt{2,3}.txt`):

```text
+ DataStage maps file columns BY POSITION, never by header text (headers in the file may differ from the job's
+ column names). So: assert the column count equals the link's column count, rename with .toDF(<link column
+ names in order>), ...
+ ROW ORDER (critical): Spark views do NOT keep row order. A DataStage Sort's order flows to every downstream stage
+ until a Join, Aggregator or Funnel breaks it (it passes through Copy, Filter and Transformer). Track it, and:
+   - Head: emit `ORDER BY <the upstream sort keys> LIMIT n` - the first n rows in sort order.
+ # Self-check before answering
+ 1. Every link in the input has exactly one view (or table write), named like the link.
+ 2. Every `LIMIT` that has a Sort upstream (through Copy/Filter/Transformer) carries that Sort's `ORDER BY`.
+ 3. Every CSV source is renamed by position with .toDF(...) and has the column-count assert.
+ 4. Every output view selects exactly the output link's columns, in the link's order, with the declared types.
+ 5. No logic, column or table appears that the input does not contain.
```

- **Few-shots swapped** to J04 (CSV sources, which shows the positional read) and J15 (Sort → Copy → Head, which shows
  the order surviving a Copy). The compiler was fixed first, so the examples were correct.
- **Adaptive thinking** at high effort. The fixed thinking budget documented in Switch's
  [LLM configuration](https://databrickslabs.github.io/lakebridge/docs/transpile/pluggable_transpilers/switch/customizing_switch/)
  is rejected by this model.

Result: 4 → 0 lost `ORDER BY`, 0 → 11 of 11 positional reads, for 8% more tokens. The three changes were made
together, so we can't say which one did the work.

**Attempt #4, one rule for one bug found at run time** ([full text](switch_prompt/history/system_attempt4.txt)).
DQX validation found 9,269 NULL `customer_id` (§4 #2). The compiler was fixed, the examples regenerated, and this was added:

```text
+ EMPTY FIELDS: Spark reads an empty CSV field as NULL, DataStage reads it as "" for a non-nullable string column.
+ Wrap every non-nullable string source column in coalesce(`col`, '') - otherwise checks such as
+ `Len(Trim(x)) = 0` never fire (Len of NULL is NULL).
  (self-check 3 extended: "... and its non-nullable string columns are wrapped in coalesce(`col`, '')")
```

Result: 50 `coalesce` wraps, the same count as the compiler. 0 validation errors and 39/39 tables matching after the run.

**What carries over to other migrations:**

1. **Choose the prompt family deliberately.** The dialect decides the output style (notebook, SQL or SDP) as much
   as `target_type` does.
2. **Give the exact skeleton** (widget block, naming rule "one view per link, named like the link"). It removed
   parameter and path drift in one step, and makes outputs diffable against a reference.
3. **Few-shots outweigh rules.** Switch copied a bug from the examples in spite of the rules. Choose examples that
   contain the hard patterns (Sort → Copy → Head, CSV reads), and make sure the examples are correct.
4. **Write down the source platform's behaviour.** The model defaults to Spark's, which differs from DataStage on
   column mapping, empty strings and row order. Each of those needed an explicit rule.
5. **End with a self-check list** naming the defects you have seen. It costs little, and the defects it lists didn't come back.
6. **Condense the input.** Raw DSX is mostly repeated schema. The condensed job is 4–10× smaller (about 9× for
   most jobs) and keeps all derivations.
7. **Measure every generation**: a static diff against a reference (`compare_notebooks.py`), then a run, then
   DQX. Several defects only appeared at run time (#4).

## 4. DataStage semantics that had to be reproduced

These four issues were each found by running the pipeline or by DQX, not by reading the code. They apply to
both implementations. The Switch prompt now spells out each one.

| # | DataStage behaviour | Naive Spark behaviour | Symptom | Fix |
|---|---|---|---|---|
| 1 | Sequential File maps columns **by position**; the header text is ignored | `spark.read.csv(header=true)` + select by name | J03 failed: `UNRESOLVED_COLUMN SupplierCountry` (the file header says `Country`) | Assert the column count, then `.toDF(<declared names>)` |
| 2 | An empty field in a **non-nullable string** column is `""` | Empty CSV field → `NULL` | `If Len(Trim(CustomerID)) = 0` never fired, so 9,269 order lines had `customer_id NULL` and **`is_guest = 0` on every row**. DQX `is_not_null` caught it | `coalesce(col, '')` on non-nullable source string columns |
| 3 | A Sort's order flows through Copy/Filter/Transformer into a Head (first *n* rows in sort order) | Temp views do not keep order; a bare `LIMIT` returns arbitrary rows | Switch #2 produced wrong Top-N marts | `ORDER BY <upstream sort keys> LIMIT n` |
| 4 | Surrogate keys numbered by input row order (`@INROWNUM`) | No inherent row order | `store_sk`, `employee_sk`, `promo_sk` are only as deterministic as the file read order | `row_number() OVER (ORDER BY …)`. Reconciliation treats these keys as warnings (§6) |

## 5. DQX validation (`_dqx_validate`, last task of each run)

- **Rules:** 66 metadata rules on 19 tables (60 error, 6 warn): not-null, uniqueness of grain, allowed values,
  SCD2 invariants (`eff_start_key <= eff_end_key`, an open-ended current row), measure signs, foreign keys from
  facts to dimensions, RFM score ranges, and `audit_reconciliation.status = 'PASS'` (DataStage J23).
- **Run:** `DQEngine.validate_checks` first, then `apply_checks_by_metadata`. Results go to
  `<schema>.dq_validation_results` and failing rows to `<schema>.dq_quarantine_<table>`. The task fails the job
  on any error-level violation.
- **Final result (all three schemas: compiled, Switch, SDP):** 0 errors. Warnings, which are expected data conditions:

  | Table | Rule | Rows |
  |---|---|---|
  | fact_sales | guest_customer (customer_sk = -1) | 9,106 |
  | fact_sales | gross_profit_not_negative | 934 |
  | fact_sales | zero_price_line | 87 |
  | fact_invoice | zero_value_invoice | 44 |
  | fact_sales | orphan_product | 12 |

- **Rule corrections made along the way:** `sales_amount > 0` and `invoice_sales > 0` were too strict.
  DataStage J01 deliberately keeps zero-price lines, so these became `>= 0` (error) plus a `> 0` warning.
  Also, DQX ≥ 0.16 reads a bare string in `is_in_list(allowed=…)` as a *column*, so literals are now quoted (`'UK'`).

## 6. DQX reconciliation: Switch vs compiled (`_compare_outputs`)

The Switch output is the dataset under check; the compiled output is the reference. Everything is DQX-native:

1. One rule set per table, stored in DQX checks storage (`TableChecksStorageConfig`, table
   `unitygo.retail_dw_compare.dq_compare_checks`, `run_config_name` = table name):

   | Rule | DQX function | Severity |
   |---|---|---|
   | `schema_matches` | `has_valid_schema(ref_table, strict=True)`: same columns, order and types | error |
   | `rows_match` | `compare_datasets` on the table's natural key, `check_missing_records`, excluding input-order surrogate keys | error |
   | `surrogate_keys_match` | `compare_datasets` including `store_sk` / `employee_sk` / `promo_sk` | warn |

2. `DQEngine.apply_checks_and_save_in_tables` with one `RunConfig` per table. A `DQMetricsObserver` writes summary
   metrics to `dq_compare_metrics`. Only tables that differ are re-run with a quarantine config
   (`<table>_dq_quarantine`).
3. The report is read from DQX's per-check metrics (`check_metrics.error_count` / `warning_count`).

**Result:** 39/39 tables match. `checked_count` equals the input row count (for example, 32,575 for
`fact_sales`), so the checks really ran. A separate `EXCEPT ALL` on `fact_sales`, `dim_store` and
`product_top50` agrees: 0 differences.

Caveat: the Switch prompt uses compiled notebooks as few-shot examples, so the two implementations are
not fully independent. Agreement shows that Switch reproduced the compiler's semantics. It does not prove
the semantics independently. Validation against DataStage itself would need DataStage output for
the same inputs (see §8).

## 7. SDP version (Switch `target_type: sdp`)

The notebook versions keep DataStage's shape: one job notebook per parallel job, and a Lakeflow Job that
replays the master sequence. The SDP version keeps the *logic* but uses what
[Spark Declarative Pipelines](https://docs.databricks.com/aws/en/dlt/) provide: one pipeline whose
dependency graph replaces the sequence, and Auto CDC in place of the hand-written SCD2.

### 7.1 Design

| DataStage | SDP version |
|---|---|
| 23 job notebooks + 28-task Lakeflow Job | **One** pipeline (`bundle_sdp/resources/retail_dw_sdp.pipeline.yml`) with 21 source files. The run order comes from the dataflow, so `setup`, `check_dim_customer`, `cond_dim_missing` and `promote_dim_customer` are gone |
| Link | `@dp.temporary_view` named `<job code>_<link>` (e.g. `j04_lnk_stores`). Dataset names are pipeline-wide, and the same link names recur across jobs |
| Target file | `@dp.materialized_view` with the same name as the file, so DQX validation and reconciliation run unchanged |
| Job parameters | Pipeline `configuration` (`src_dir`, `pRunDate`, `pEffDate`) read with `spark.conf.get` |
| J02 + J05 + J06 + check + promote (customer SCD2) | One **dimension unit** (`J02_J05_J06_Dim_Customer_Unit.py`), see below |

**SCD2 with Auto CDC from snapshots.** In DataStage, SCD2 takes a 20-stage job (J06), a conditional
initial-load job (J05), an "exists?" check and a file-move promote step. The Analyzer rates J06 VERY_HIGH, and
re-runs apply the 2011 snapshot again (§8). Switch generated this design:

```python
dp.create_streaming_table(name="dim_customer_history")

def next_snapshot_and_version(latest_version):      # 2010 = version 1, 2011 = version 2
    if latest_version is None: return (staged_snapshot(2010), 1)
    if latest_version == 1:    return (staged_snapshot(2011), 2)
    return None

dp.create_auto_cdc_from_snapshot_flow(target="dim_customer_history", source=next_snapshot_and_version,
    keys=["customer_id"], stored_as_scd_type=2, track_history_column_list=["attr_hash"])
```

`staged_snapshot(year)` is J02's standardisation (positional read, `coalesce`, trims, CRC32 `attr_hash`). It is
a plain function, so the CDC flow never depends on a pipeline dataset, and the `stg_customers_*` materialized
views use the same function. Tracking history on `attr_hash` reproduces DataStage's change test exactly.
`dim_customer` / `dim_customer_next` are materialized views over the history table, which recompute
DataStage's columns from `__START_AT` / `__END_AT`: `version_no = row_number() OVER (PARTITION BY customer_id ORDER BY __START_AT)`,
`customer_sk = customer_id * 1000 + version_no`, `eff_start_key` 19000101 or `pEffDate`, `eff_end_key` 99991231
or `pEffDate − 1`, and `is_current`. Auto CDC remembers which snapshot versions it has processed, so a re-run
doesn't apply 2011 again.

### 7.2 Prompt and runs

Prompt: [`switch_prompt/datastage_to_sdp.yml`](switch_prompt/datastage_to_sdp.yml), built by
[`build_prompt_sdp.py`](switch_prompt/build_prompt_sdp.py). Config: [`switch_config_sdp.yml`](switch_config_sdp.yml)
(`target_type: sdp`, `sdp_language: python`). The stage, function and DataStage-semantics rules are the notebook
prompt's (§3, §4). New in this prompt:

- **The output shape**, as above: modern API only (`@dp.temporary_view`, `@dp.materialized_view`,
  `spark.read.table`), no `dbutils`, writes, actions or qualified names.
- **Switch's built-in SDP guidance is left out on purpose.** The prompt does not reference
  `${common_sdp_instructions_and_guidelines}`. That guidance uses legacy APIs (`@dp.view`, `dp.read`), forbids the
  `spark.sql` this translation relies on, and asks for hard-coded `catalog.schema.table` names. Switch combines the
  prompts by OmegaConf substitution, so leaving the placeholder out removes the guidance completely.
- **An "SCD Type 2 dimension unit" rule**, without an example: don't translate expire/carry/insert/promote stage
  by stage. Stage the snapshots in a plain function, add a history streaming table and
  `create_auto_cdc_from_snapshot_flow` with a version callback, and derive the target files from `__START_AT` /
  `__END_AT` using the jobs' own derivations.
- **Few-shots:** J04 and J15 rendered by a new `ds2spark.py --sdp` mode (`sdp_reference/`). That mode emits the
  same translation as SDP. Before Switch ran, it was deployed for J01 + J04 and the pipeline completed with the
  same row counts as the compiled version, which confirmed the pattern works.
- **Input:** the 20 single-job files plus one dimension unit (`switch_input_sdp/J02_J05_J06_Dim_Customer_Unit.txt`).
  The unit is the three condensed jobs plus a short header that states the sequence's orchestration (initial
  load only if the dimension is missing, apply 2011, promote). That header is written by hand; it summarises
  `pipeline_dag.json`, because this information exists only in the sequence.

| Run | What | Result |
|---|---|---|
| Switch `70464911684866` | 21 files, `max_fix_attempts: 1` | 21/21 converted (185k tokens). **Every** file reported the same SDP validation error (`DataflowGraph.validate.Unresolved`), even J01, which has no dependencies. Switch validates each file in a throwaway pipeline that has none of our `configuration`. Its fix-up step then "repaired" every file by inventing `src_dir` defaults such as `/Volumes/main/default/source_data` |
| E2E `334701512237490` | Pipeline → DQX validate → DQX compare | Pipeline **succeeded first time**, validation clean. Compare: 25/39. `dim_customer_next` (SCD2 output) matched **exactly**, but `dim_customer` had 94 rows instead of 948, and 12 downstream tables followed |
| Switch `533534559691383` | Customer unit only, prompt clarified, `max_fix_attempts: 0` | `dim_customer` and `dim_customer_next` both built from the post-snapshot state. No invented defaults |
| E2E `1120547313076486` | As above | Pipeline + validation SUCCESS, **37/39 match** |

The prompt fix after the first E2E run: *"Downstream jobs read the dimension AFTER the orchestration has
run, i.e. after every snapshot has been applied and the 'next' file promoted - so the dimension and its 'next'
file have the SAME content … never just the initial load."* The first wording ("materialized views with the
names of the dimension's target files") let Switch map the J05 output to `dim_customer` literally.

### 7.3 Result and the two remaining differences

DQX validation of `retail_dw_sdp` gives the same result as the compiled version: 0 errors, and the same five
warnings with the same counts. Reconciliation against `retail_dw_compiled`: **37/39 tables match**,
`dim_customer_history` exists only in SDP (by design), and two tables differ:

| Table | Difference | Cause | Verdict |
|---|---|---|---|
| `audit_scd2_customer` | Compiled: `U` 935. SDP: `N` 841, `C` 13, `U` 81 | The **compiled reference** comes from repeated runs. Once `dim_customer` exists, J05 is skipped and J06 compares 2011 with an already-2011 dimension, so everything is "unchanged". SDP reports the correct first-load counts and keeps them on re-runs | Reference artefact, not an SDP defect. To compare like with like, the compiled reference needs a clean first run (drop its customer-dimension tables, then re-run) |
| `basket_affinity` | 128 rows | J19 keeps the top 1,000 pairs sorted **only** by `pair_count`. The 876 pairs above the cutoff (`pair_count` > 14) are identical. 124 of the pairs tied at 14 are kept, and which 124 is undefined, both in DataStage and in either Spark version | Non-determinism inherited from the source. A tie-break key in J19 would make it testable |

### 7.4 What we learned

1. **The SCD2 pattern converts well.** Given a rule but no example, Switch produced a correct
   Auto-CDC-from-snapshot design whose output equals the hand-written 20-stage job, and it fixes the re-run problem.
2. **Hand the LLM the orchestration context.** The SCD2 semantics live partly in the sequence (initial-load
   condition, promote). Sending the jobs as one unit with that context was needed, and the one ambiguous sentence
   about promote was the one real defect.
3. **Switch's SDP validation runs without your pipeline configuration.** If files read `spark.conf`, expect it to
   fail on every file. Set `max_fix_attempts: 0`, or the fix-up step invents defaults. The 20 single-job files
   in `bundle_sdp/` come from the first run and still contain these defaults. They are harmless because the
   pipeline configuration takes precedence, but they would hide a missing configuration, so regenerate them with
   `max_fix_attempts: 0` before production use.
4. **The real validation is a pipeline run plus DQX.** Here only a full pipeline update, followed by validation
   and reconciliation, gave a meaningful answer.
5. **Reconciliation exposed problems in the reference too:** the re-run state of the compiled SCD2, and a
   non-deterministic top-N in the source job.

## 8. Open items and known limitations

- **BladeBridge produces no notebooks** (§3). It needs one genuine DataStage Designer XML export to tell
  whether our XML shape or the tool is at fault. Alternatively, raise a Lakebridge issue with the logs we collected.
- **No comparison against DataStage output.** `Output_Data/` holds outputs of the *original* 4 jobs, not the
  23-job pipeline. Running the DataStage jobs on the same inputs and reconciling (Lakebridge Reconcile or
  DQX `compare_datasets`) is the remaining proof of equivalence.
- **Failure notifications not migrated** (`exc_Any_Failure`, `act_Notify_*`). Add `email_notifications` /
  webhooks to the job.
- **SCD2 re-runs (notebook versions).** As in the DataStage sequence, a re-run skips J05 and applies the 2011
  snapshot again to the promoted `dim_customer`, so `audit_scd2_customer` reports everything as unchanged. The SDP
  version (§7) doesn't have this problem, because Auto CDC tracks processed snapshot versions.
- **Clean first run of the compiled reference.** Needed to reconcile `audit_scd2_customer` against SDP (§7.3).
  It means dropping `dim_customer`, `dim_customer_next` and `audit_scd2_customer` in `retail_dw_compiled` before the
  master job runs. Not done yet: it needs approval, because it deletes tables.
- **Non-deterministic top-N in J19** (`basket_affinity`): sorted only by `pair_count`, so ties at the cutoff are
  arbitrary in every implementation (§7.3). Adding a tie-break (e.g. `stock_code`, `stock_code_b`) is a change to
  the source logic and should be agreed first.
- **SDP files with invented defaults.** 20 of the 21 SDP files still contain the `src_dir` defaults added by
  Switch's fix-up step (§7.4). Regenerate them with `max_fix_attempts: 0`.
- **Input-order surrogate keys** (`store_sk`, `employee_sk`, `promo_sk`) depend on file read order. Consider
  ordering them by the natural key.
- **Reconciliation runtime.** The first version took 326 s for 39 small tables. Several changes meant to speed it
  up (parallel rule saves, `raise_on_duplicate_keys`, parallelism 4→12, metrics-only first pass, conditional
  quarantine) made it **566 s**. This hasn't been profiled yet. The suspects are that changing the rule
  fingerprints forced all 39 rule sets to be rewritten, and that 12 concurrent `replaceWhere` writers to one checks table
  conflict and retry. Profile before changing it further.
- **Environment pinning.** Jobs use serverless environment version 5. Version 2 rejects `DataFrame.cache()`.
- **Cost.** Each Switch run uses about 0.5M tokens on `databricks-claude-sonnet-5-5`.

## 9. How to run

Prerequisites: Databricks CLI ≥ 1.0, profile `DEFAULT` on the workspace, and `CREATE SCHEMA` on catalog
`unitygo`. The source CSVs go in `/Volumes/unitygo/retail_dw/landing`.

```bash
# regenerate code (local, no workspace needed)
python3 migration/dsx_to_xml.py "DataStage Jobs/Pipeline" migration/xml   # XML for Lakebridge Analyzer
python3 migration/ds2spark.py                                              # compiled notebooks
python3 migration/build_bundle.py                                          # job YAML + support notebooks
python3 migration/dsx_condense.py "DataStage Jobs/Pipeline" migration/switch_input
python3 migration/switch_prompt/build_prompt.py                            # Switch prompt (few-shots from compiled)

# deploy and run (compiled)
cd migration/bundle && databricks bundle deploy -t dev && databricks bundle run retail_dw_master -t dev

# Switch: install once, then convert. Set conversion_prompt_yaml in migration/switch_config.yml to your
# workspace path and upload it to /Workspace/Users/<you>/.lakebridge/switch/resources/switch_config.yml
databricks labs lakebridge install-transpile --include-llm-transpiler true
databricks labs lakebridge llm-transpile --input-source migration/switch_input_jobs \
  --output-ws-folder /Workspace/Users/<you>/retail_dw_switch_nb_vN --source-dialect unknown_etl \
  --catalog-name unitygo --schema-name retail_dw --volume switch_volume \
  --foundation-model databricks-claude-sonnet-5-5 --accept-terms true
# export the notebooks into migration/bundle_switch/src/notebooks, then deploy/run bundle_switch

# reconcile the two schemas
cd migration/bundle && databricks bundle run retail_dw_compare -t dev

# SDP version: few-shots, prompt, Switch (upload switch_config_sdp.yml as the Switch config), then run end-to-end
python3 migration/ds2spark.py --sdp                                        # sdp_reference/ (few-shots)
python3 migration/switch_prompt/build_prompt_sdp.py                        # datastage_to_sdp.yml
databricks labs lakebridge llm-transpile --input-source migration/switch_input_sdp \
  --output-ws-folder /Workspace/Users/<you>/retail_dw_switch_sdp --source-dialect unknown_etl \
  --catalog-name unitygo --schema-name retail_dw --volume switch_volume \
  --foundation-model databricks-claude-sonnet-5-5 --accept-terms true
# export into migration/bundle_sdp/src/pipeline, then:
cd migration/bundle_sdp && databricks bundle deploy -t dev && databricks bundle run retail_dw_sdp_e2e -t dev
```

Two operational notes. With two CLI profiles on the same host, Lakebridge's inner Python needs
`DATABRICKS_CONFIG_PROFILE=DEFAULT` exported. `switch_input_jobs/` is `switch_input/` without the master sequence.
